# 한국형 커뮤니티 통합 실행 플랜

작성·상태 확인: **2026-10-13 · v4 · 메모·이름 저장·전달 연결, 공개 반영·검증 완료**

행정사무소의 목적을 담고, 전직·취업·창업·교육·생활·보훈의 질문과 경험이 쌓이는 커뮤니티를 만든다. 대상은 20~50대, 주 이용자는 2030이다. 읽기·찾기·쓰기의 편안함, 자연스러운 한국어, 실제 운영 가능성, 개인정보 최소수집을 제품의 기준으로 삼는다.

이 문서는 기존 조사, 10월 5일 구현, GitHub 공개 모음, Claude 사이클 4, Fable 새 제작과 후속 비교를 연결한 **통합 실행 기준과 현행 진행 기록**이다. 10월 13일에는 페이지 연결·기본 통합을 진행한 뒤, 사용자의 외관 피드백과 A–Z 이상 조합 선택 요청에 따라 Claude 기능판의 디자인 선택·비교·적용까지 범위를 넓혔다. 이어 사용자가 메모·다른 이름 저장·에이전트 수정 요청의 연결을 다시 요구해 같은 기능판에 복원했다. 이 추가분은 로컬·공개 검증을 완료한 상태이다. 아래 현재 상태와 13절은 실행 결과이며, 나머지 로드맵은 후속 계획이다. 최종 디자인 채택·기존 정적 저장 데이터 자동 이전·실회원 서비스 구축이 완료되었다는 뜻은 아니다.

**실행 순서: 산출물 연결 → 화면 선택·통합 → 실제 회원 흐름 구현 → 제한 베타 → 공개 운영 → 수익화.**

**1. 현재 어디까지 왔는가**

| 묶음 | 확인한 상태 | 앞으로의 역할 |
|---|---|---|
| 목적·사용자 요구·상용 사이트 조사 | 기존 인터뷰와 디자인 비교 기록 있음. 간격·목록 밀도·모바일 배치·이미지 표시 방식의 관찰을 축적 | 디자인 결정의 근거로 재사용. 관찰을 실사용 수요로 확대 해석하지 않음 |

| Fable 새 제작 | `577ce8b`. 새 제작과 인계 완료. 화면별 옆 안내, 폭별 구성, 게시판/문답/카드 전환 및 상태별 화면 증거 있음 | 비교 후보와 부분 이식의 근거 |
| Claude–Fable 비교 | 각각 120조합에서 15개 자동 항목 통과. 가린 모델 검토 1회와 비교 보고까지 완료 | 추가 제작을 시작하기보다 채택할 차이를 결정할 자료 |
| 실서비스 | 실제 인증·DB·서버 권한·회원 운영은 미구현 | 이번 플랜의 구현 단계에서 처음 연결 |

공개 모음의 `publication/`과 Claude가 수정한 `community/`는 서로 다른 페이지 묶음이다. 새 공개 사본의 `candidates/claude/`와 `candidates/fable/`에 허용한 소스를 옮기고, 실행 화면·공통 복귀 링크·버전·출처를 연결했다. 기존 정적 편집기는 보존했으며 React 후보와 설정을 공유하지 않는다. 기존 Claude 작업 폴더와 미추적 측정 결과 전체를 공개하거나 수정하지 않았다. 이전 디자인 조합 배포에서는 실제 공개 주소의 후보와 공개 소스 접근을 확인했다. 이번 메모·이름 저장·전달 추가분도 공개 반영과 익명 접근을 확인했다.

10월 12일 Fable 실험과 비교는 완료된 근거로 유지한다. 이후 사용자는 기능판의 외관이 기존 A/B/C보다 후퇴했다고 지적하고 더 많은 출발 시안과 독립 축 조합을 요청했다. 이에 디자인 선택 기능을 추가했으며, Fable 전체 채택이나 사용자의 최종 외관 선택을 받은 것으로 기록하지 않는다.

자동 통과는 해당 소스와 검사 범위의 결과다. 과거 120조합 비교는 로그인 전 화면 중심이며, 루트 글자 크기 변경은 브라우저 줌과 다르다. 이번에는 두 후보에서 390px 체험 로그인·글·댓글·저장·내 활동·계정 분리·초기화를 직접 검증해 빠진 핵심 동선을 확인했다. 합성 입력과 메모리 시연 검증이며 실회원 서비스 검증은 아니다. 새 디자인 스타일 반영 뒤 같은 핵심 동선도 다시 통과했다. 모델의 선호 점수는 최종 채택이나 실사용 만족도를 대신하지 않는다.

**2. 모든 단계에서 이어갈 제품 요구**

| 영역 | 유지할 요구 |
|---|---|
| 기본 이용 | 비회원은 글·댓글·자료를 읽고, 작성 의사가 생기면 로그인한다. 일반 글쓰기에 출처나 정형 답변을 강요하지 않는다. |
| 정보 구조 | 홈·커뮤니티·자료실·이용 안내·내 활동·글쓰기. 홈은 최근 대화와 주제 진입이 보이는 커뮤니티 첫 화면이다. |
| 탐색 | 제목을 훑고 검색·주제·상황·정렬로 좁힌다. 상세에서 돌아올 때 목록 조건과 읽던 위치를 유지한다. |
| 디자인 | 좌우 여백·제목·메타정보·조작의 위계를 맞춘다. 모바일과 데스크톱의 정보 배치를 각각 설계한다. |
| 조절과 전달 | 화살표 구성 전환, 세부 색상·글꼴·밀도·폭·이미지 설정, 메모, 다른 이름 저장, 내보내기·복원을 보존한다. |
| 신뢰 | 공식 자료·운영자 안내·회원 경험·광고를 구분한다. 합성 예시는 실제 활동·조회·답변 대기 건수로 표시하지 않는다. |
| 브랜드 | 별표·별꽃 기호를 기본 브랜드로 사용하지 않는다. 최종 이름·로고는 실제 화면을 보고 결정한다. |
| 사업 방향 | 기본 읽기·쓰기의 무료 이용 방향을 유지한다. 광고·제휴·유료 기능은 운영 검증 뒤 별도로 결정한다. |
| 협업 | 페이지·원본 코드·버전·변경 이유·남은 결정이 하나의 공개 입구에서 이어진다. 개인 대화 기록을 공개할 필요는 없다. |

‘AI 밤티’는 폰트나 색 하나를 금지하는 방식으로 판정하지 않는다. 과한 도입부, 반복 카드, 불필요한 아이콘, 부정확한 간격, 어색한 문구, 내용 없는 활동 수치가 실제 화면에 있는지 살핀다. 기존 디자인 skill과 자동 측정은 이 판단을 돕는 도구로 사용한다.

**3. 단계별 실행과 종료 조건**

| 단계 | 실제로 할 일 | 남길 산출물 | 이 단계가 끝나는 조건 |
|---|---|---|---|
| **0 · 결과 연결** | Claude/Fable의 현재 커밋과 필요한 화면 증거를 묶고, 오래된 WORKSPACE의 완료·미완료를 현재 상태에 맞춘다. 기존 공개 모음에 두 후보와 이 계획을 연결할 변경안을 준비한다. | 기존 모음의 갱신안, 후보별 실행 화면·코드·버전 링크 | 처음 온 사람이 별도 대화 설명 없이 기존 시안·Claude·Fable의 역할과 차이를 확인한다. 공개 반영 시에는 익명 접근도 확인한다. |
| **1 · 화면 선택과 통합** | 동일한 과제로 후보를 비교하고 채택할 화면과 요소를 정한다. 선택한 구현 한 곳에 필요한 변경을 모으고 편집·메모·저장 기능을 연결한다. | 선택된 통합 체험판 1개, 채택/보류 이유, 좁힌 수정 목록 | 읽기·찾기·작성·복귀·설정 저장·메모 전달이 이어진다. 기본 구성이 하나로 정해지고 남은 외관 제안은 후속 목록으로 이동한다. |
| **2 · 실제 회원 흐름** | 배포·인증·DB 공급자를 정하고 공개 HTML, 서버 세션, 글·댓글 저장, 서버 권한, 신고·삭제를 연결한다. 개인정보·복구 설계를 이때 구현한다. | 테스트 계정으로 사용할 수 있는 실제 저장형 서비스 | 두 계정 사이 권한 침범이 차단되고, 새로고침 후 저장·삭제·세션 동작이 맞는다. 삭제 및 복구 시험을 통과한다. |
| **3 · 제한 베타** | 운영자·연락 창구·답변 범위·정책을 확정한다. 소규모 이용자가 핵심 과제를 수행하고, 운영자는 신고 처리·복구·사고 대응을 연습한다. | 베타 결과와 해결된 결함, 실제 운영 문서 | 핵심 행동을 막는 결함이 해결되고, 담당자와 비용 한도·복구 수단이 준비된다. |
| **4 · 공개 운영** | 공식 도메인과 공개 콘텐츠를 연결한다. 검색 노출을 열고, 익명 방문·모바일·공유·접근 권한·캐시를 실제 호스트에서 확인한다. | 공개 서비스 주소, 되돌릴 배포 버전, 운영 현황 | 로그인 없는 읽기, 회원 작성, 신고/삭제 대응, 검색 접근이 실제 배포에서 동작한다. |
| **5 · 운영 개선과 수익** | 실제 재방문·답변·운영 부담·비용을 보고 개선한다. 광고·제휴부터 작은 범위로 검토하고 유료 기능의 수요를 확인한다. | 근거 있는 개선/사업 결정 | 특정 유료 기능의 필요·운영 비용·사용자 영향을 설명할 수 있을 때만 구현한다. |

단계 0·1의 시안 공개와 단계 4의 실회원 서비스 공개는 서로 다른 완료 상태다. 이번 작업은 별도 공개 사본의 검토된 코드와 합성 체험 화면을 기존 모음에 연결한다. Claude 원본 작업을 덮어쓰거나 실회원 모집을 진행하는 작업은 아니다. 이전 연결·디자인 조합 범위는 검증과 공개 확인을 완료했다. 이번 메모·이름 저장·전달 추가분은 같은 완료 기록을 그대로 적용하지 않고 로컬 검증과 새 공개 확인을 진행한다.

3개월은 확정 일정으로 두지 않는다. 우선 이번에 정한 단계 0·1의 연결·디자인 선택·메모·이름 저장·전달 범위를 끝내고, 단계 2의 공급자·운영 범위가 정해지면 실제 구현량을 기준으로 일정을 확정한다. 공급자나 브랜드 결정 대기를 이유로 독립적으로 가능한 화면 정리까지 멈추지는 않는다.

**4. 실행 순서 — 완료된 연결과 후속 선택**

1. **원본 버전 기록 완료.** Claude `38a207d`, Fable `577ce8b`를 후보별로 기록하고 공개용 소스·실행 화면·조정 내용을 연결했다. 완료된 Fable 제작이나 120조합 측정을 다시 시작하지 않았다.
2. **기존 모음 연결 구현 완료.** 후보 두 화면과 이 계획·종료 조건을 기존 카탈로그에 추가하고 총 21개 항목을 연결했다. 별도 플랫폼은 만들지 않았다. 원격 공개 반영과 익명 접근 확인도 완료했다.
3. **핵심 체험 동선 확인.** 두 후보의 390px 화면에서 목록·상세·뒤로가기·직접 주소와 새로고침, 체험 로그인 후 글·댓글·저장·내 활동·계정 분리·초기화와 모음 복귀를 확인했다. 새 디자인 스타일 반영 뒤 해당 동선도 다시 통과했다. 이전의 120조합 측정 행렬을 반복하는 대신 바뀐 디자인 선택과 주요 동선을 검사한다.
4. **디자인 선택 기능 구현.** Claude 기반 기능판에서 A–AF 32개 출발 조합과 7개 독립 축을 선택하고 실제 홈을 나란히 비교·취소·적용할 수 있다. 최종 외관 선택은 사용자에게 남긴다. 권장 기능 출발점은 Claude 기반판이다. Fable의 화면별 옆 안내·중간 폭 구성·메뉴·구성 전환에서 유용한 부분을 선택해 이식한다. Fable 전체를 기본으로 바꾸려면 기존 동작과 편집 기능 보존을 함께 확인한다. 한 번의 모델 평가만으로 기본안을 뒤집지 않는다.
5. **현재: 메모·이름 저장·전달을 연결한다.** 위치에 4색 메모를 남기고 편집·완료·삭제하며, 임시본과 명시 저장본을 구분한다. 다른 이름 저장은 원본을 보존하고 JSON 가져오기는 별도 사본으로 연다. JSON·Markdown·독립 시각 참고 HTML 다운로드까지 검증한 뒤 공개 화면과 소스·결과를 인계한다. 최종 외관 선택과 실회원 구현은 후속이다.

비교 기준은 먼저 **과제를 끝낼 수 있는가**, 다음으로 **읽기·탐색이 편한가**, 마지막으로 **원하는 인상인가**다. 글자 확대에서 잘 버티는 것과 작은 첫 화면에 글이 많이 보이는 것은 각각 살핀다. 첫 화면 행 수를 늘리기 위해 글자를 과도하게 줄이지 않는다.

**5. 화면과 편집 기능을 어떻게 통합할 것인가**

| 화면/기능 | 통합 방향 | 확인할 점 |
|---|---|---|
| 홈 | 최근 글·주제 진입을 먼저, 자료실·사무소 안내를 다음에 배치 | 도입 문구가 대화를 지나치게 밀어내지 않는가 |
| 목록 | Claude의 제목 중심 행과 연한 보조 필터 위계를 우선 참고 | 긴 제목, 빈 결과, 상황 정보, 댓글 상태를 쉽게 구분하는가 |
| 상세 | 본문·댓글을 주인공으로 두고 관련 글 등 화면에 맞는 옆 안내 적용 | 목록 복귀 맥락, 긴 본문 줄 길이, 댓글 입력 공간이 편한가 |
| 모바일·태블릿 | 탐색·필터·옆 안내의 위치를 폭과 글자 크기에 맞춰 재배치 | 내 활동과 핵심 조작이 사라지지 않고 메뉴가 본문을 압도하지 않는가 |
| 글쓰기 | 체험/실제 로그인 뒤 제목·본문·분야·상황·초안/등록 흐름 | 로그인 안내만 확인하고 작성 검증을 완료 처리하지 않았는가 |
| 사무소 답변 | 답변 있음/미답변의 구분은 유지하되 실제 운영 상태를 표시 | 합성 글 12개를 실제 사무소 미답변 12건으로 표현하지 않는가 |
| 구성 전환 | 게시판·문답·카드 같은 빠른 프리셋과 상세 설정을 함께 제공 | 프리셋을 추가하면서 기존 색·밀도·이미지 설정을 잃지 않는가 |
| 메모·저장 | 안정된 페이지/요소 식별자로 메모를 연결하고 설정 버전 포함 | 다른 이름 저장이 원본을 덮지 않고 다른 브라우저에서도 내보낸 파일을 복원하는가 |

기존 정적 편집기의 A/B/C와 네 가지 목록 구성, Fable의 세 가지 구성은 보존한다. Claude 기반판에는 A–AF 32개 출발 조합과 **화면 구성 / 색상 / 목록 / 글꼴 / 여백 / 모서리 / 기호**의 독립 축을 연결했다. 32개는 같은 기능판을 다르게 조합한 출발점이다. 디자인 선택 패널에서 같은 1280px 홈을 나란히 비교하고 취소·적용할 수 있으며, 적용한 설정은 브라우저에 저장된다. 비교 화면 안에서는 조작할 수 없다.

설정 전환은 검색 조건·글 주소·작성 초안·권한을 바꾸지 않는다. 메모에는 페이지, 요소, 설정 조합, 기준 버전을 넣는다. 에이전트 전달 문서는 ‘현재 모습 → 원하는 변화 → 이유’가 보이게 한다. Claude 기능판 자체에 위치 메모·이름 저장과 JSON 복원·Markdown 수정 요청·독립 시각 참고 HTML을 연결해 이번에 검증한다. JSON 가져오기는 별도 사본이며 기존 저장본을 덮지 않는다. 구 정적 편집기는 삭제하지 않았고 저장 키·형식이 달라 자동 이전하지 않는다. HTML은 화면과 메모를 보여 주는 참고 파일이며 실제 회원 서비스나 편집 가능한 기능판은 아니다.

저장본은 30개, 시안별 메모는 100개, 메모 내용은 2,000자, 시안 이름은 80자, 가져오는 JSON은 1MB 이하로 제한한다. 4색 메모의 편집·완료·삭제와 저장본 관리를 지원하며, 에이전트 전달은 내려받은 파일로 진행한다. 자동 전송이나 원격 에이전트 실행은 하지 않는다.

**6. 기술은 현재 코드를 이어받고, 운영에 필요한 것부터 연결한다**

현재 기능 체험판은 Vite/React, 공개 미리보기는 정적 생성물이다. Next.js·Tailwind·shadcn을 한꺼번에 도입하는 전면 재작성은 즉시 작업에 넣지 않는다. 단계 2 시작 때 공개 글 HTML 제공과 회원 권한을 포함한 **글 한 건의 전체 흐름**을 구현하면서 필요한 기술 결정을 끝낸다.

| 계층 | 이번 계획의 기본 방향 | 도입 시점 |
|---|---|---|
| 저장소·산출물 | 기존 GitHub 공개 모음과 원본 버전 추적을 유지. 공개 가능한 파일만 분리 | 단계 0 |
| 화면 | 기존 React 구성과 검증된 UI 재사용. 선택된 스타일을 한 구현에 반영 | 단계 1 |
| 공개 콘텐츠 렌더링 | 글·자료의 제목/본문/출처가 최초 HTML 응답에 있어야 함. SSG/SSR 방식은 선택한 호스트에서 검증 | 단계 2 |
| 운영 호스팅 | Cloudflare Workers를 우선 검토. 도메인·캐시·실제 보안 헤더·비용 차단 동작까지 설정 | 단계 2~4 |
| 인증·DB | 공개 콘텐츠용 PostgreSQL 1곳, 관리형 인증 1곳. 신원 저장과 콘텐츠 저장의 권한·백업·유출 범위를 먼저 정하고 공급자를 선택 | 단계 2 |
| 공급자 후보 | Neon + 별도 인증, 또는 Supabase 기반 경로를 비교해 하나를 선택. 실제 접속 방식에 필요한 경우에만 Hyperdrive 검토 | 단계 2 시작 때 결정 완료 |
| 이미지 | 운영자 제공 이미지부터 승인된 변환본을 사용. R2는 실제 저장 경로가 필요해질 때 연결 | 단계 2 이후 |
| 검색·알림 | 한국어 제목·본문 검색과 앱 내 알림부터. 벡터 검색·추천·실시간 연결은 측정된 필요가 있을 때 추가 | 기본 검색은 단계 2, 확장은 이후 |
| CI·운영 | 선택한 커밋의 빌드·관련 기능/권한 검사·배포·되돌리기. 공급자 비용 알림과 앱의 사용 제한을 별도로 구성 | 단계 2~3 |

공급자 이름은 확정 구매나 계정 생성 지시가 아니다. DB를 두 곳에 중복 운영하거나 인증을 겹쳐 붙이지 않는다. Next.js를 선택할 경우 당시 Cloudflare 공식 지원 경로와 런타임 호환성을 확인한다. 현재 공식 안내도 바뀌고 있으므로 ‘Next.js 15+면 Pages/Workers에 그대로 된다’는 가정으로 구현하지 않는다. [Cloudflare 프레임워크 안내](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/).

Supabase Auth는 프로젝트의 PostgreSQL 안에 인증 데이터를 보관하므로 스키마를 나누는 것만으로 DB 전체 유출에 대비한 신원 분리가 완성되지 않는다. ‘콘텐츠 저장소 전체가 유출되어도 인증 식별자는 별도 보호’라는 목표를 적용하려면 독립된 인증 저장 경계가 필요하다. 공급자 선택 때 이 조건을 실제 권한·백업 구조로 확인한다. [Supabase 인증 구조](https://supabase.com/docs/guides/auth).

**7. 개인정보·보안은 회원 기능의 첫 설계에 포함한다**

목표는 **수집·연결·보관되는 개인정보와 사고 시 피해를 줄이고, 실제 의무를 이행할 수 있는 구조**다. 유출 시 자동 면책되는 안전지대를 약속하지 않는다. 안전조치와 유출 통지·신고는 설계 문구만으로 충족되지 않으며 운영에서 수행해야 한다. [개인정보 보호법 제29조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0029&lsiSeq=283839&urlMode=lsScJoRltInfoR), [제34조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0034&lsiSeq=283839&urlMode=lsScJoRltInfoR).

| 영역 | 설계·구현할 것 | 완료 증거 |
|---|---|---|
| 최소수집 | 실명·군번·부대·전체 생년월일·신분/건강 증빙을 기본 입력에서 제외. 연락처가 필요한 목적은 별도로 정함 | 데이터 항목마다 목적·근거·기간·접근자·파기 경로가 있음 |
| 신원과 공개 글 | 인증 식별자, 내부 소유권, 공개 프로필/글, 신고 정보를 나누고 접근 권한·키·백업 범위도 분리 | 공개 API·HTML·검색에 인증 정보와 운영 메모가 포함되지 않음 |
| 권한 | 서버가 세션으로 작성자·운영자를 판단. 모든 수정·삭제·신고 처리에 권한 검사 | 계정 A가 B의 글·신고·운영 데이터에 접근하는 부정 요청 차단 |
| 운영자 보호 | 관리자 MFA·최소권한·감사기록. 토큰·요청 본문·민감 검색어의 로그 유출 방지 | 실제 관리자 접근과 로그 표본 확인 |
| 삭제·복구 | 공개 차단 → 원본/연결/자체 검색/피드/CDN 정리 → 보존 필요분 격리 → 백업 만료 및 복원 후 재삭제 | 삭제한 시험 데이터가 복구 후 다시 노출되지 않음 |
| 게시 내용 | 글 본문에 들어오는 타인 정보·연락처·민감 내용을 신고·비공개·수정할 절차 | 실제 신고 접수와 처리, 작성자 안내가 동작 |
| 계약·권리행사 | 운영 주체·연락 창구·수탁/국외이전·연령/보호자 절차·처리방침을 실제 공급자와 맞춤 | 운영 담당자 및 필요한 계약/설정 확인 |
| 사고 대응 | 접근 차단·키 교체·증거 보전·피해 파악·통지/신고 담당과 절차 | 모의 사고에서 담당자가 절차를 수행함 |

가명·해시·익명 표시를 자동 익명화로 간주하지 않는다. 같은 권한으로 모두 읽을 수 있는 테이블을 나누기만 해서는 유출 범위를 충분히 줄이지 못한다. 초기에는 원본 신분·군·건강 자료를 업로드받지 않는 방향을 유지한다. 외부 검색·AI 서비스에 이미 복제된 글의 완전 회수는 보장하지 않는다.

HTML/XSS 처리, 세션·CSRF, 요청 크기와 빈도, 악성 업로드, 종속성 업데이트는 실제 서버 경로에서 다룬다. Turnstile·WAF·Rate Limit은 보조 수단으로 적용하고 서버 권한 검사를 대체하지 않는다. 개인정보 검토가 필요해지는 시점은 실회원 연결 전이며, 시안 비교를 끝내지 못하게 만드는 추가 디자인 과제로 취급하지 않는다.

**8. 일반 검색과 AI 검색을 같은 콘텐츠 기반 위에 만든다**

공개 가능한 원문을 사람이 읽고 검색·AI 시스템도 접근할 수 있게 만든다. 시안과 합성 체험 글은 실제 지식 콘텐츠로 색인시키지 않는다. 회원 글의 공개·검색 노출 범위는 게시 전에 이해할 수 있게 한다.

- 글·자료마다 안정된 개별 주소, 고유 제목, 실제 본문, 작성/수정 시각, 관련 링크를 제공한다. 공개 주소의 최초 HTML에 주요 내용이 있어야 한다.
- 공식 자료에는 원문 출처·적용 범위·확인일을 적고 잘못된 안내의 정정 경로를 둔다. 질문·경험 글을 억지로 ‘200~300자 정답’ 형식으로 바꾸지 않는다.
- 구조화 데이터는 실제 페이지 성격과 일치시킨다. 실제 토론에만 토론 데이터를 사용하고 가짜 댓글·평점·작성자를 만들지 않는다.
- canonical·sitemap·피드·공유 메타데이터·404/410과 내부 링크를 정리한다. 탈퇴/삭제가 자체 검색·피드·캐시에 반영되게 한다.
- 검색 수집과 모델 학습 수집의 허용 정책을 구분한다. robots/noindex를 개인정보 접근 통제로 사용하지 않는다.
- 검색 유입과 AI 인용을 글의 유용성·재방문·작성으로 이어지는지 함께 본다. 검색 순위나 인용을 보장하지 않는다.

Google의 최신 안내도 일반 SEO와 고유하고 유용한 콘텐츠를 기반으로 설명한다. AI 검색을 위한 별도 요령보다 위 공개 콘텐츠 구조를 먼저 완성한다. [Google 생성형 AI 검색 최적화 안내](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).

계측에서는 Google Search Console의 생성형 AI 성과 보고서를 활용한다. 2026년 공식 안내에는 전 세계 배포와 노출·페이지 등의 항목이 명시되어 있다. 이 보고서를 ChatGPT·Perplexity 등 모든 서비스의 인용 통계로 해석하지 않는다. 다른 서비스는 유입 정보와 일정한 질문 표본에서 확인한 인용을 구분해 기록한다. [Google 보고서 안내](https://developers.google.com/search/blog/2026/06/gen-ai-performance-reports).

**9. 이미지·오픈소스·상업적 이용**

기존 결과에는 Flarum MIT CSS 일부 이식과 고지, CC0 사진 두 종의 변환본이 있다. 이 자산과 출처 기록을 이어가고, 새 코드나 이미지를 추가할 때 원본 URL·버전·라이선스·수정 내용을 함께 남긴다. 공개 저장소라는 이유만으로 상업적 재사용을 허용받았다고 판단하지 않는다. 코드 라이선스와 로고·폰트·사진·게시물의 권리를 각각 확인한다.

기존 이미지의 160/320/640/1200px, AVIF/WebP/JPEG 변환과 표시 비율 예약을 계승한다. 실제 슬롯에 맞는 `srcset/sizes`, 화면 아래 이미지의 지연 로딩, 주요 첫 화면 이미지의 우선 로딩을 적용하고 전송량과 레이아웃 이동을 확인한다. 사진이 없는 글에는 빈 사진 상자를 강제하지 않는다. 회원 업로드는 크기·형식 검증, 재인코딩·메타데이터 처리, 접근 통제·삭제 흐름까지 갖춘 뒤 연다.

보안은 코드 비공개에 의존하지 않는다. 클라이언트에 비밀키를 넣지 않고 권한은 서버에서 검사한다. 공개 모음에는 검토된 코드·샘플·출처만 내보내며 실제 회원 데이터·개인 대화·내부 운영 기록을 포함하지 않는다.

**10. 공개 전에 정할 운영과 사업의 최소 범위**

| 결정 | 필요한 시점 | 잠정 방향 |
|---|---|---|
| 최종 이름·도메인·운영 주체 | 공개 운영 전 | 시안 정리는 중립 이름으로 진행 가능 |
| 사무소 답변 책임·응답 범위 | 실제 답변 기능 운영 전 | 누가 답할지 정해진 범위만 약속. 미답변 상태와 상담 접수는 구분 |
| 신고·삭제·개인정보 연락 창구 | 실회원 베타 전 | 담당자와 처리 절차를 먼저 확보 |
| 가입·연령·인증 공급자 | 실제 로그인 구현 전 | 필요 데이터와 가입 가능 범위를 확인한 단일 경로 |
| 회원 글 검색 노출·민감정보 정책 | 실회원 게시 전 | 공개 범위를 명확히 알리고 수정·삭제 경로 제공 |
| 콘텐츠 수급·검수 | 베타 시작 전 | 공식 안내와 실제 작성 글 중심. 합성 글로 활발한 커뮤니티처럼 꾸미지 않음 |
| 월 비용 상한·비상 차단 | 유료 인프라 연결 전 | 알림뿐 아니라 비싼 기능의 요청 제한·중단 동작 준비 |
| 광고·제휴·프리미엄 | 기본 운영 검증 후 | 광고 표시와 개인정보 영향을 검토. 월 구독료·우선 노출을 지금 확정하지 않음 |

AI는 초기에는 운영자용 분류·중복 후보·신고 검토 보조부터 검토한다. 자동 제재나 전문 상담 답변을 첫 출시의 필수 기능으로 두지 않는다. 도입 시에는 외부 전송 데이터·보존·비용·사람의 검토와 이의제기 절차를 함께 설계한다. 알릴 필요가 있는 AI 사용을 숨기는 것을 제품 미감의 기준으로 삼지 않는다.

베타에서는 찾기→읽기→복귀, 작성→댓글, 본인 수정/삭제, 신고의 소수 핵심 과제를 실제 이용자에게 확인한다. 클릭 수만 보지 않고 실패 지점과 혼동한 문구를 기록한다. 운영 단계에서는 재방문, 질문의 응답 상태, 신고 처리 시간, 삭제 처리, 월 비용을 함께 본다.

**11. 꼬리물기를 막는 작업 규칙**

1. 한 작업은 **사용자 문제 하나 또는 명시한 산출물 묶음**으로 시작한다. 끝에는 화면/코드 링크, 기준 커밋, 해결 결과, 남은 선택만 남긴다.
2. ‘측정기 보완’, ‘다른 모델에게 재채점’, ‘더 많은 레퍼런스’는 실제로 해결할 결함이나 미결정이 있을 때만 추가한다. 자동으로 다음 사이클을 열지 않는다.
3. 기존 통과 결과는 버전·범위와 함께 재사용한다. 소스 변경이나 실패가 없는 전체 검사를 습관적으로 반복하지 않는다.
4. 취향이 갈리는 부분은 선택할 수 있는 화면 차이로 보여 준다. 한 번의 시각 검토와 수정 후에도 남은 취향 차이는 사용자의 선택이나 후속 목록으로 넘긴다. 권한·데이터 손실 같은 결함은 해결될 때까지 해당 출시를 막는다.
5. 결함을 고치는 검증과 제품 방향을 정하는 비교를 구분한다. 점수나 화면 조합 수를 완료 목표로 삼지 않는다.
6. 기존 작업 담당과 파일 영역을 확인한 뒤 수정한다. 진행 중인 다른 에이전트의 작업을 덮어쓰거나 무단으로 중단하지 않는다.
7. 완료한 일은 이 문서와 현행 WORKSPACE에 즉시 반영한다. 과거 감사·스케치에는 당시 날짜와 상태를 유지한다.
8. 공개 카탈로그의 항목은 최소한 `이름 · 종류 · 상태 · 화면 URL · 소스 경로/버전 · 갱신일 · 핵심 한계`를 갖는다. 기존 manifest를 활용하고 별도 관리 체계를 늘리지 않는다.
